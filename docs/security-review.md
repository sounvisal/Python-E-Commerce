# LUMÉA security review

November 23, 2026 · Reviewed revision `cc402b1`

This ECC review covered the Vue storefront and admin console, the FastAPI routes, the Vercel and Render configuration, and the tracked dependency files. Local tests used disposable SQLite databases. The findings below apply to the reviewed source or Git history. Live configuration, real customer data, Neon behavior, and the previously deferred KHQR flow were outside this pass.

## Fix before the next release

1. **High · Public notifications disclose purchase activity.** The endpoint is publicly readable. Its purchase payload combines the customer's first name and last initial, delivery city, purchased product, relative time, and internal order ID. A one-word name can be published in full. Changing the display name alone still leaves a record of an individual purchase. The same feed exposes codes from active promotions regardless of whether staff intended to publish them. **Fix:** Remove individual orders from the public feed. Put account-specific activity behind ownership checks. Give promotions an explicit public visibility setting and enforce their active dates and redemption limits. The public response should contain zero order identifiers or customer details. [Feed](../python-backend/app/api/notifications.py#L40)

2. **High · Git history contains database snapshots.** I verified that commit `e920fc7` is an ancestor of `origin/main` and that its two SQLite files contain user, order, and return tables. The larger snapshot has 8 user rows, 87 order rows, and 9 return rows. Counts alone do not establish whether records are real or synthetic. **Fix:** Have the repository owner establish what data was retained and who had access. Rotate any real credentials found, assess affected accounts, and approve any history cleanup with the team. Add a Git check for databases and secret files. Previous clones and forks need separate consideration.

3. **High · Return details use email as proof of ownership.** Registration checks for an exact email match. The return detail route compares lowercased emails, and its list route uses exact equality. Different accounts can therefore be treated as the same owner by one route. **Fix:** Resolve ownership through the original order's customer ID for both routes. Review and backfill historical rows before removing legacy lookup code. Migrate email normalization and uniqueness after detecting collisions. Add a test that two distinct accounts can never cross-read returns. [Return detail](../python-backend/app/api/returns.py#L55) · [Registration](../python-backend/app/api/auth.py#L15)

4. **High · Disposable accounts can tie up cash-on-delivery stock.** Registration issues a session immediately without email or phone verification. Order creation requires that session, but COD orders reserve stock immediately and get no expiry. There is no per-account cap on open COD orders in the order creation path. **Fix:** Verify a contact channel before a first COD order, cap open orders and reserved quantities per account, and expire unconfirmed reservations with an auditable stock release. Apply stronger checks to unusual order volume. Test that repeated rejected or expired orders cannot permanently consume stock. [Registration](../python-backend/app/api/auth.py#L45) · [Order reservation](../python-backend/app/api/orders.py#L338)

5. **High · Request limits are weak against automated abuse.** The limiter uses a process-local counter per IP and exact path. Routes that include an order ID, product slug, or other parameter do not share a route-level budget. Limits reset on restart. The development test-header exception is reachable whenever production mode is off. Anonymous contact submissions also write immediately and inherit the generic API allowance. **Fix:** Remove test bypasses from the served app and use test dependency overrides. Enforce route-group and global budgets at a trusted ingress, then add tighter login, registration, contact, and checkout budgets keyed by both verified client identity and account where available. Confirm correct proxy IP handling and equivalent protection on the direct backend origin. [Rate limiting](../python-backend/app/core/rate_limit.py#L70) · [Contact form](../python-backend/app/api/contact.py#L32)

6. **High · Dispatch and cancellation can produce inconsistent stock.** Cancellation uses a conditional database update before releasing stock. The normal fulfillment path validates a previously loaded status and then directly updates it. Concurrent requests can overwrite the result of cancellation and leave an order marked shipped after the reservation was released. **Fix:** Use one atomic state transition with the expected state and inventory changes in the same transaction. Test competing dispatch and cancellation on PostgreSQL, with exactly one outcome and consistent inventory. Apply the same approach to reward-credit writes. [Order state transitions](../python-backend/app/services/order_lifecycle.py#L55)

## Next hardening batch

7. **High if enabled · Private return photos share public asset storage.** The return form uses the general upload route. The public static mount serves saved files without checking return ownership. Upload endpoints also trust filename extensions, accumulate file contents in memory, and lack an explicit application-level total byte budget for batches. **Fix:** Store return evidence privately and authorize each download. Check file signatures, enforce file count, aggregate size, and account quotas at ingress and storage, and stream uploads to quarantined storage. Protect historical evidence before enabling hosted uploads. [Return form](../frontend/src/views/returns/ReturnRequestView.vue#L472) · [Upload handling](../python-backend/app/api/upload.py#L68) · [Public mount](../python-backend/app/main.py#L166)

8. **Medium · Login lookups are ambiguous and can perform excessive database work.** Email sign-in passes the identifier to a pattern comparison, and the phone fallback loads every account with a phone number and compares suffixes in Python. Password verification still runs, but identity selection can be ambiguous and requests get more expensive as customer count grows. **Fix:** Use indexed, exact matches on canonical email and verified international-format phone numbers. Handle existing duplicates before enforcing uniqueness. Align registration and verification on a single password policy, including bcrypt's byte limit or a migration to Argon2id. [Login lookup](../python-backend/app/api/auth.py#L56) · [Password handling](../python-backend/app/core/security.py#L7)

9. **Medium · Admin sessions have broad exposure.** A seven-day bearer token is persisted in browser storage. The storefront and admin share an origin, so JavaScript running on that origin can access the saved admin token. Vercel's route config does not set a Content Security Policy for the static apps. **Fix:** Give admin shorter sessions and MFA. Use a separate admin origin and secure HttpOnly sessions with CSRF protection where cookies are used. Apply a restrictive Content Security Policy and frame protections on the hosting layer. Confirm that customer-origin code cannot access admin credentials. [Admin session storage](../admin/src/stores/auth.js#L7) · [Token lifetime](../python-backend/app/core/config.py#L30) · [Vercel routes](../vercel.ts#L12)

10. **Medium · Account-owned orders still receive legacy guest access tokens.** New orders require sign-in, but checkout still returns an order token, and order access accepts it without requiring the account that owns the order. That makes the token a second, long-lived credential for viewing personal delivery details and cancelling an eligible order. **Fix:** Require account ownership for all account-owned orders. Keep a narrow legacy path only for genuinely unclaimed guest orders, with expiry, revocation on claim, and audit logs that omit token values. [Token issuance](../python-backend/app/api/orders.py#L409) · [Order authorization](../python-backend/app/services/order_lifecycle.py#L19)

11. **Medium · Reviews and catalog requests have limited protection against bulk abuse.** Unverified accounts can submit repeated reviews for one product and cast votes across newly created accounts. Moderation protects publication but staff and the database still absorb submissions. Public product list and featured routes accept an uncapped result limit, and checkout accepts an unbounded number of item lines. **Fix:** Add per-account submission budgets, duplicate review constraints, and verified-contact requirements where appropriate. Cap result sizes and item counts at the API, paginate callers, and bound costly query parameters and request bodies. [Review submissions](../python-backend/app/api/reviews.py#L93) · [Catalog limits](../python-backend/app/api/products.py#L12) · [Checkout schema](../python-backend/app/schemas/order.py#L12)

12. **High advisory severity · Two indirect npm dependencies need an update.** The npm registry audit reported `follow-redirects` and `source-map-js` in both apps' production dependency graphs. This advisory result establishes affected dependency versions, while browser exposure depends on what the build actually uses. **Fix:** Update both lockfiles to compatible patched resolutions, rerun the audit and both builds, and verify the deployed artifacts. Pin Python's transitive production dependencies and add a Python advisory scan to the same release gate. [Storefront lockfile](../frontend/package-lock.json) · [Admin lockfile](../admin/package-lock.json) · [Python requirements](../python-backend/requirements.txt)

## Verification

- **Builds:** Both Vercel-style Vue builds passed on the final checked source. An earlier build during notification edits failed on duplicated frontend code and recovered after the source changed.
- **Tests:** 13 storefront tests passed. The selected backend suite produced **84 passed, 3 failed, 14 deselected**, with **65% Python statement coverage**. Two tests still create guest orders directly after the route was changed to require an authenticated customer. The concurrent last-unit test also uses that old setup and never verifies the intended race. Update these fixtures and keep explicit checks for anonymous denial and legacy order ownership.
- **Scanning:** A filename and source-pattern scan of current application files did not find matching private keys or embedded database credentials. The historical database check found the snapshots described above. npm production advisory scans completed for both apps. No historical secret scanner, Python advisory scan, configured lint or type check, live abuse test, or PostgreSQL run was completed.
- **Release decision:** Hold the next production release until the high-priority privacy and inventory items and the failing regression checks are resolved. The next verification should use synthetic customers on disposable PostgreSQL and confirm that the public feed reveals no private data.
