# Remaining-flow implementation pass

10 November 2026. This extends the selected fixes in `FLOW_FIXES_FIRST_PASS.md`; it does not mark the entire original audit complete.

## Implemented

- **Authentication and privacy:** sign-in/registration failures remain failures; forged offline sessions are removed. Remember me uses persistent storage when selected and session storage otherwise. Session startup validates `/auth/me`; expired credentials clear private state. New accounts have empty addresses, payment methods, purchases, and diary entries. Account switches load separately scoped quiz, journal, and wishlist records. Profile names/phone numbers and addresses now save to the backend; unsupported saved-card actions are disabled.
- **API permissions:** the admin router requires an actual administrator role. Content/settings mutations also require admin access; uploads and review submission require login. Customer order/return lists are scoped on the server. New orders bind the authenticated user ID; guessing an order number or supplying another email does not grant access. Legacy purchases without a checkout key retain account-email access for compatibility.
- **Guest purchases:** creation returns an order-scoped credential kept in browser session storage and sent as `X-Order-Token`. Guest tracking uses `/track/:orderNumber`. Customers can claim a guest purchase only with that credential and the matching account email. Unclaimed guest access currently depends on retaining that browser session.
- **Checkout and inventory:** clients send a persistent random checkout key. Replaying the same request returns the same order and credential without consuming inventory twice; changing the bag with the same key is rejected. A retry quote recognizes inventory already reserved for that attempt. Conditional database stock updates prevent two checkouts buying the final unit. Cancellation and expiry release inventory and coupon capacity once. A backend worker sweeps expired checkouts every 30 seconds, with additional cleanup during order/quote access.
- **Payment and fulfillment:** QR generation cannot overwrite a bank settlement received while extraction is running. Unverifiable QR fallbacks are rejected rather than presented as automatically confirmable payments. KHQR therefore requires a working configured live verification bridge; COD remains available when verification is unavailable. Late settlement becomes Payment Review and tells the customer not to pay again. Duplicate settlement cannot rewind shipment. Staff fulfillment follows guarded stages; completing COD delivery records collection. Customers cannot advance courier status. Paid cancellation requires a refund review rather than pretending money was returned.
- **Order views:** fabricated history and unknown-order confirmations are removed. Cancellation updates the display only after server acknowledgement. Timelines use recorded events rather than invented times. Reorder resolves actual product IDs against current prices/availability and preserves quantities. Guest tracking and order lookup display real errors. Quote changes update displayed discount values before resubmission.
- **Promotions:** percentage promotions persist in the database. Admin edits, active dates, pausing, and redemption limits affect validation and checkout. Usage is reserved during placement and released on unpaid cancellation/expiry. Initial `LUMEA10`, `ATELIER15`, and `LUMEA20` rules are migrated once; restarting does not reactivate a paused promotion. Unsupported gift/shipping/bundle campaign creation is no longer offered as a functioning feature.
- **Articles and banners:** article drafts/body/tags/published state persist; public article APIs exclude unpublished records. Admin lists load real records, including unpublished content, instead of merging fixtures. Banner editing and visibility save through the existing API; unsupported homepage metadata/templates are hidden. The home hero respects its saved visibility setting. Other page layouts still need a visual/visibility pass.
- **Product editor:** skin attributes, subcategory, and gallery are saved; editing does not automatically unfeature the product. Existing galleries are preserved on edit, nullable media fields can be cleared, invalid prices/negative stock are rejected, and category selection must reference a real category.
- **Returns and reviews:** return progression uses canonical stages and derives the customer timeline. Refund completion requires a recorded manual refund reference; it does not initiate a bank transfer. Returns use delivery time when recorded and purchase time for legacy records. Download now provides real return instructions rather than claiming a prepaid label. Reviews derive identity/purchase verification from the account and order, start pending moderation, and helpful votes are limited to one per account. Moderation updates product rating aggregates.
- **Support and operational truth:** contact submission stores a durable inquiry and returns a reference. An authenticated admin inbox at `/support` displays the inquiries. There is no claim that an email was sent. Backend revenue/timeline metrics use actual paid orders and dates. Order payment filters work; unsupported courier/date controls are disabled. Several misleading zero-count fallbacks were removed. The settings download explicitly describes itself as settings only, rather than a database backup.

## Database activation and compatibility

The backend applies additive schema updates on startup after table creation and before seeding. New nullable columns and conservative defaults preserve existing purchases; legacy orders are not given stock reservations or reclassified as paid/unpaid automatically. New support, promotion, and helpful-vote tables are created normally.

The actual `lumea.db` was not altered during this coding pass. Migration was exercised twice against an in-memory copy of that database, with the original order count retained. The changed backend must be restarted before using the changed frontends against an existing running service.

Changed API contracts include order-scoped credentials for guests, authenticated customer lists, admin-only mutations, checkout keys for retry safety, and persisted promotion validation. Older smoke scripts that relied on public administrative access are no longer valid acceptance tests.

## Verification

- 38 backend tests pass in `test_security_transactions.py` (including inherited first-pass tests). They cover route permission dependencies, ownership, guest claim, idempotency, quotes, pricing, inventory release, a simultaneous two-checkout final-unit race, payment timing, promotions, drafts, moderation, contact persistence, returns, and repeatable migrations.
- 13 frontend/rule tests pass with `node --test frontend/tests/flows.test.mjs test_recommendations.mjs`. Store tests exercise actual bundled Pinia stores with controlled Axios responses and storage, including offline failures, Remember me, account switching, failed saves/cancellations, catalog replacement, and promotion validation.
- Storefront and admin production builds pass; existing bundle-size warnings remain.
- Backend modules compile and edited source files decode as UTF-8.
- Backend regressions invoke route handlers and inspect permission registration; they are not a full HTTP/server or live-bank integration suite. No real transactions or external messages were sent.

## Still open

Live bank settlement, complete desktop/mobile journeys, accessibility, and responsive visual QA remain unverified. Automatic bank refunds, card/wallet gateways, actual variant SKUs, email/OAuth/password-reset delivery, a full restorable database/assets backup, and cross-device diary/quiz synchronization are not implemented. Unsupported operations are disabled or described honestly where addressed in this pass.

The wider audit still has work: admin category ordering/menu visibility, the admin quiz editor's connection to storefront questions/rules, remaining static analytics/customer widgets and placeholder controls, some public content/error/brand fallbacks, richer return/replacement/credit branches, and consistent filters/pagination across all views. Historical payment records require reconciliation against real evidence. Banner visibility outside the home hero and visual behavior of the new forms/inbox need browser verification.
